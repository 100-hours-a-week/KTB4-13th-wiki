# EC2 MySQL vs RDS

처리 성능이 아니라 **장애 복구와 운영 부담이 핵심입니다**. 예상 부하인 약 200 QPS, 검증 기준 400 QPS는 EC2 MySQL도 충분히 처리할 수 있으므로, 사용자 수나 QPS만으로 RDS가 필요한 것은 아니라고 판단합니다.

EC2 2노드 Primary–Standby도 데이터 복제는 가능하지만, 네트워크 단절처럼 Primary의 종료 여부가 불분명한 장애에서는 안전한 자동 전환이 어렵습니다. 기존 Primary가 살아 있는 상태에서 Standby를 승격하면 두 서버가 동시에 쓰기를 처리하는 Split-brain이 발생할 수 있습니다.

- split-brain
  - DB가 서로를 확인하지 못하는 상황에서 양쪽 모두 자신을 Primary라고 판단해 쓰기를 받는 장애

이를 방지하려면 EC2 구성에 다음 요소가 추가로 필요합니다.

- 기존 Primary를 확실하게 차단하는 Fencing
  - Fencing
    - 새로운 Primary를 승격하기 전에 기존 Primary를 확실히 종료하거나 네트워크에서 격리하는 것
- 장애 판정을 위한 외부 Witness
  - Witness
    - Primary와 Standby 중 어느 서버가 정상인지 판단하는 데 참여하는 제3의 관찰자
- 승격을 제어하는 오케스트레이터와 분산 잠금
  - 오케스트레이터
    - 장애 조치 과정을 자동으로 실행하는 관리자
  - 분산 잠금
    - 여러 오케스트레이터가 동시에 서로 다른 Standby를 승격하지 못하도록 하는 장치
- 고정된 접속 주소를 제공하는 DNS 또는 Proxy
  - DNS는 고정된 이름이 새로운 Primary의 IP를 가리키게 하는 방식이고, Proxy는 중간 안내 서버가 새로운 Primary로 연결해 주는 방식
- 자동 전환이 필요하다면 과반수 결정을 위한 3노드 구성
  - DB 서버끼리 투표해서 누가 새로운 Primary가 될지 결정하기 위해 필요한 최소 노드수

이를 하지 않는다면 2노드에서 수동 장애 조치를 사용하여 엔지니어가 장애를 확인하고 기존 Primary 차단, Standby 승격, DNS 변경과 기존 서버 재합류를 수행해야 합니다. 이는 담당자의 대응 시간과 판단에 따라 복구 시간이 달라지므로 RTO 5분을 지속적으로 달성하기 어렵고, 잘못된 승격이나 차단 누락과 같은 휴먼에러가 발생할 수 있습니다.

RDS Multi-AZ는 다른 가용영역에 동기식 Standby를 유지하며 다음 작업을 AWS가 관리합니다.

- Primary 장애 감지
- 기존 Primary 격리
- Standby 자동 승격
- 동일한 DB Endpoint의 연결 대상 변경
- 장애 인스턴스 교체와 Standby 재구축
- 자동 백업과 시점 복구
- OS 패치와 기반 인프라 관리

따라서 RDS를 선택하는 이유는 QPS 처리 성능보다 **네트워크·가용영역 장애 시 안전한 자동 복구, RTO 5분 달성 가능성, 휴먼에러와 운영 부담 감소**에 있습니다.

다만 RDS도 장애 조치 과정에서 기존 DB 연결이 종료될 수 있으므로 애플리케이션에는 연결 재시도와 주문·결제 멱등성 처리가 필요합니다.

참고: [RDS Multi-AZ 공식 문서](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html), [RDS 장애 조치 공식 문서](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZ.Failover.html)

# Amazon RDS 배포 방식

Amazon RDS의 배포 방식은 크게 다음 세 가지로 나눌 수 있습니다.

1. Single-AZ DB instance
2. Multi-AZ DB instance
3. Multi-AZ DB cluster

먼저 장애 복구와 관련된 용어를 이해해야 합니다.

- **AZ(가용 영역)**: 하나의 AWS 리전 안에 있는 독립된 데이터센터 영역입니다.
- **장애 조치(Failover)**: 현재 Writer에 장애가 발생했을 때 대기 인스턴스를 새로운 Writer로 전환하는 과정입니다.
- **RTO**: 장애가 발생한 뒤 서비스를 다시 사용할 수 있을 때까지 걸리는 시간입니다.
- **RPO**: 장애로 인해 잃을 수 있는 데이터의 범위입니다.

## 한눈에 비교하기

| 구분 | Single-AZ | Multi-AZ DB instance | Multi-AZ DB cluster |
| --- | --- | --- | --- |
| 인스턴스 구성 | Writer 1대 | Writer 1대 + Standby 1대 | Writer 1대 + Reader 2대 |
| AZ 수 | 1개 | 2개 | 3개 |
| 복제 방식 | 기본 복제 없음 | 동기식 | 반동기식 |
| 자동 장애 조치 | 불가능 | 가능 | 가능 |
| 대기 인스턴스 읽기 | 없음 | 불가능 | 가능 |
| 읽기 부하 분산 | 불가능 | 별도 Read Replica 필요 | Reader endpoint로 가능 |
| 일반적인 용도 | 개발·테스트, 비용 절감 | 고가용성 | 고가용성 + 읽기 확장 + 빠른 커밋 |

# 1. Single-AZ DB instance

## 구조


```text
AZ-A
└─ Writer DB
```

하나의 AZ에 하나의 RDS 인스턴스만 존재하는 구성입니다.

여기서 Single-AZ는 해당 AZ에 DB를 한 대만 만들 수 있다는 뜻이 아닙니다. 같은 AZ에 여러 DB 인스턴스를 만들 수 있지만, 각각은 별개의 Single-AZ 배포입니다.

중요한 점은 Writer를 대신할 관리형 대기 인스턴스가 없다는 것입니다.

## EC2 컴퓨팅 인스턴스만 고장 난 경우

RDS DB 인스턴스는 다음 요소로 구성됩니다.

```text
EC2 기반 컴퓨팅
        +
데이터를 저장하는 EBS 볼륨
```

컴퓨팅 인스턴스만 고장 나고 EBS 볼륨은 정상이라면 RDS가 같은 AZ에 새로운 컴퓨팅 인스턴스를 만들고 기존 EBS 볼륨을 연결해 복구할 수 있습니다.

```text
기존 컴퓨팅 장애
        ↓
같은 AZ에 새 컴퓨팅 생성
        ↓
기존 EBS 볼륨 연결
        ↓
DB 복구
```

이 경우 기존 데이터가 담긴 EBS를 그대로 사용하므로 일반적으로 RPO는 0입니다. 복구 시간은 상황에 따라 다르지만 보통 30분 이내일 수 있습니다.

DB 엔드포인트도 그대로 유지되므로 애플리케이션의 연결 주소를 변경할 필요는 없습니다. 다만 장애 당시 완료되지 않은 트랜잭션은 롤백될 수 있습니다.

## EBS 볼륨까지 복구할 수 없는 경우

EBS 볼륨이 손상되거나 기존 인스턴스를 복구할 수 없으면 백업을 이용해 새로운 RDS 인스턴스를 만들어야 합니다.

RDS는 일반적으로 다음 자료를 이용해 복원합니다.

- 정기적으로 생성한 DB 스냅샷
- S3에 저장한 트랜잭션 로그
- 특정 시점 복구, 즉 PITR

복구 흐름은 다음과 같습니다.

```text
마지막 스냅샷 복원
        ↓
그 이후 트랜잭션 로그 적용
        ↓
새 RDS 인스턴스 생성
        ↓
애플리케이션 연결 변경
```

복구 가능한 최신 시점은 `LatestRestorableTime`으로 확인할 수 있습니다. 상황에 따라 최근 수분의 데이터가 복구되지 않을 수 있습니다.

새 인스턴스를 만드는 시간과 트랜잭션 로그를 적용하는 시간이 필요하므로 RTO는 데이터베이스 크기와 변경량에 따라 수십 분에서 수 시간까지 길어질 수 있습니다.

새 인스턴스에는 새로운 엔드포인트가 생성됩니다. 애플리케이션의 연결 정보를 변경하거나, 기존 인스턴스를 삭제한 뒤 새 인스턴스가 기존 이름을 사용하도록 구성해야 합니다.

## AZ 전체에 장애가 발생한 경우

```text
AZ-A 장애
└─ Writer DB 사용 불가
```

Single-AZ에는 다른 AZ의 대기 인스턴스가 없으므로 자동 장애 조치를 수행할 수 없습니다.

선택할 수 있는 방법은 다음과 같습니다.

- AZ가 복구될 때까지 기다립니다.
- 백업을 사용해 다른 AZ에 새로운 DB 인스턴스를 복원합니다.

AZ 장애가 일시적이면 인스턴스 상태는 정상으로 표시되면서 실제 접속은 되지 않을 수도 있습니다. 따라서 애플리케이션 수준의 모니터링이 필요합니다.

## Single-AZ의 한계

- AZ 장애에 자동 대응할 수 없습니다.
- DB 복구에 오랜 시간이 걸릴 수 있습니다.
- OS 패치나 유지 관리 중 DB를 사용하지 못할 수 있습니다.
- 별도의 Read Replica가 없다면 읽기 부하를 분산할 수 없습니다.

따라서 가용성이 중요한 운영 환경보다는 개발·테스트 환경이나 비용을 우선하는 시스템에 적합합니다.

> 그럼 우리 서비스는 수 시간 중단을 감수할 수 있는 서비스인가 → x → 최소한 멀티 az 구성이 적절

# 2. Multi-AZ DB instance

## 구조

```text
AZ-A                         AZ-B
Writer ─────동기식 복제────▶ Standby
읽기·쓰기 처리               접속 불가능
```

서로 다른 두 AZ에 인스턴스가 하나씩 배치됩니다.

- Writer는 읽기와 쓰기 요청을 처리합니다.
- Standby는 장애 조치를 위해 대기합니다.
- Standby는 일반적인 읽기 요청을 처리할 수 없습니다.
- 데이터는 Writer에서 Standby로 동기식 복제됩니다.

## 동기식 복제란

애플리케이션이 데이터를 저장하면 Writer와 Standby 양쪽에 기록된 후 커밋 성공이 반환됩니다.

```text
애플리케이션 → Writer에 저장
                    ↓
              Standby에도 저장
                    ↓
             커밋 성공 응답
```

따라서 정상적인 장애 조치 상황에서는 커밋이 완료된 데이터가 Standby에도 존재합니다. 일반적으로 RPO는 0으로 봅니다.

그 대신 원격 AZ의 Standby가 기록을 완료할 때까지 기다려야 하므로 쓰기 지연 시간이 증가할 수 있습니다.

## 자동 장애 조치가 발생하는 상황

RDS는 다음과 같은 상황에서 자동 장애 조치를 수행할 수 있습니다.

- Writer가 있는 AZ에 장애가 발생한 경우
- Writer와의 네트워크 연결이 끊긴 경우
- Writer의 컴퓨팅 인스턴스에 장애가 발생한 경우
- Writer의 스토리지에 장애가 발생한 경우

장애가 발생하면 다음 과정이 진행됩니다.

```text
Writer 장애 감지
        ↓
Standby를 새 Writer로 승격
        ↓
DB 엔드포인트의 DNS 변경
        ↓
애플리케이션 재연결
```

일반적인 장애 조치 시간은 약 1~2분이지만, 트랜잭션 복구량이나 스토리지 성능 등에 따라 더 길어질 수 있습니다.

장애 조치 과정에서는 기존 DB 연결과 실행 중이던 쿼리가 종료될 수 있습니다. 따라서 애플리케이션에 연결 재시도와 트랜잭션 재처리 기능이 필요합니다.

## 장애 조치 이후의 상태

```text
장애 전

AZ-A             AZ-B
Writer            Standby

장애 후

AZ-A             AZ-B
장애 ✕            새 Writer
                  Standby 없음
```

장애 조치 직후에는 기존 Standby가 Writer가 되므로, RDS가 새로운 Standby를 구성할 때까지 일시적으로 대기 인스턴스가 없는 상태가 될 수 있습니다.

## 읽기 부하를 분산하려면

Multi-AZ DB instance의 Standby는 읽을 수 없습니다. 읽기 부하를 분산하려면 별도의 Read Replica를 추가해야 합니다.

```text
                 ┌─▶ Standby
Writer ──────────┤    장애 조치용, 읽기 불가능
                 └─▶ Read Replica
                      읽기용, 비동기식 복제
```

Standby와 Read Replica는 목적이 다릅니다.

| 구분 | Standby | Read Replica |
| --- | --- | --- |
| 목적 | 자동 장애 조치 | 읽기 부하 분산 |
| 복제 | 동기식 | 비동기식 |
| 읽기 요청 | 불가능 | 가능 |
| 장애 시 승격 | RDS가 자동 처리 | 일반적으로 별도 승격 필요 |

## 장애 예상 영향

Peak 50 RPS 기준

| 장애 시간 | 전체 요청 | 조회 요청 83% | 변경 요청 17% |
| --- | --- | --- | --- |
| 1분 | 최대 3,000건 | 약 2,490건 | 약 510건 |
| 2분 | 최대 6,000건 | 약 4,980건 | 약 1,020건 |

## 가용성 목표와 비교

30일 기준 가용성 99.9%는 월 약 43분의 중단을 허용합니다.

- 1분 장애 1회: 월 허용 시간의 약 2.3%
- 2분 장애 1회: 월 허용 시간의 약 4.6%
- Failover 1회만 고려한 가용성: 약 99.995%

# 3. Multi-AZ DB cluster

## 구조


```text
AZ-A                 AZ-B                 AZ-C
Writer               Reader 1            Reader 2
읽기·쓰기            읽기 가능            읽기 가능
```

Multi-AZ DB cluster는 서로 다른 세 AZ에 다음 인스턴스를 배치합니다.

- Writer 1대
- 읽기 가능한 대기 인스턴스 2대

두 Reader는 평상시에 읽기 요청을 처리하면서 Writer 장애 시 새로운 Writer 후보로도 사용됩니다.

현재 이 구성은 지원되는 버전 및 리전에 한해 RDS for MySQL과 RDS for PostgreSQL에서 사용할 수 있습니다.

## 엔드포인트 구분

애플리케이션은 목적에 따라 엔드포인트를 나눠서 사용합니다.

### Writer endpoint

다음 요청에 사용합니다.

- `INSERT`, `UPDATE`, `DELETE`
- 방금 저장한 데이터를 반드시 읽어야 하는 `SELECT`
- 최신 데이터가 필요한 조회

### Reader endpoint

두 Reader에 읽기 요청을 분산할 때 사용합니다.

- 일반 조회
- 통계 조회
- 상품 목록 조회
- 약간의 복제 지연을 허용할 수 있는 조회

```text
쓰기 요청 ─────────────▶ Writer endpoint
읽기 요청 ─────────────▶ Reader endpoint
                              ├─ Reader 1
                              └─ Reader 2
```

## 로컬 SSD와 EBS 사용

각 인스턴스는 다음 두 종류의 스토리지를 함께 사용합니다.

- 빠른 트랜잭션 로그 기록을 위한 로컬 NVMe SSD
- 데이터를 장기 보관하기 위한 EBS 볼륨

쓰기 과정은 단순화하면 다음과 같습니다.

```text
1. Writer의 로컬 SSD에 트랜잭션 로그 기록
2. Reader 중 한 대의 로컬 SSD에도 로그 기록
3. 애플리케이션에 커밋 성공 응답
4. 이후 로그 내용을 각 인스턴스의 데이터에 적용
5. 연결된 EBS 스토리지에도 반영
```

빠른 로컬 SSD에 트랜잭션 로그를 먼저 기록하기 때문에 커밋 지연 시간을 줄일 수 있습니다.

AWS는 워크로드와 구성에 따라 기존 Single-AZ 또는 Multi-AZ DB instance보다 트랜잭션 커밋 지연 시간이 최대 2배 빨라질 수 있다고 설명합니다.

## 반동기식 복제와 2-out-of-3 쿼럼

Multi-AZ DB cluster는 반동기식 복제를 사용합니다.

클러스터의 세 인스턴스 중 두 인스턴스가 쓰기를 확인하면 커밋할 수 있습니다.

```text
Writer + Reader 1 = 커밋 가능
Writer + Reader 2 = 커밋 가능
```

Writer는 Reader 두 대가 모두 응답할 때까지 기다리지 않습니다. 둘 중 한 대만 트랜잭션 로그 기록을 확인하면 커밋을 완료할 수 있습니다.

이를 `2-out-of-3 quorum`, 즉 3개 중 2개 쿼럼이라고 합니다.

### Reader 하나의 경로가 느린 경우

```text
Writer → Reader 1 : 지연 또는 장애
Writer → Reader 2 : 정상 응답
```

Reader 2가 확인하면 Writer와 Reader 2로 쿼럼이 충족됩니다. 따라서 느린 Reader 1을 기다리지 않고 쓰기를 계속 처리할 수 있습니다.

반대로 Reader 2에 문제가 발생해도 Reader 1이 정상이면 커밋할 수 있습니다.

다만 Reader 두 대가 모두 Writer와 통신할 수 없다면 쿼럼이 만들어지지 않으므로 정상적으로 쓰기를 커밋할 수 없습니다.

## AZ 장애 복원력이 높은 이유

복원력이 높아지는 핵심은 Reader가 읽을 수 있다는 사실보다 **서로 다른 AZ에 대기 인스턴스가 2대 존재한다는 점**입니다.

### Multi-AZ DB instance에서 Writer AZ가 중단된 경우

```text
AZ-A 장애        AZ-B
Writer ✕         새 Writer
                 대기 인스턴스 없음
```

Standby가 Writer로 승격되면 RDS가 새로운 Standby를 만들 때까지 대체 인스턴스가 없는 상태가 될 수 있습니다.

### Multi-AZ DB cluster에서 Writer AZ가 중단된 경우

```text
AZ-A 장애        AZ-B             AZ-C
Writer ✕         새 Writer        Reader/Standby
```

Reader 중 한 대가 Writer로 승격되어도 다른 Reader가 남습니다.

따라서 다음과 같은 장점이 있습니다.

- Writer 장애 조치 후보가 2대입니다.
- 하나의 AZ가 중단돼도 두 인스턴스가 남습니다.
- 한 복제 경로에 장애가 발생해도 다른 Reader를 이용할 수 있습니다.
- Writer를 승격한 뒤에도 Reader 또는 Standby 역할의 인스턴스가 남습니다.

`읽기 가능한 대기 인스턴스 2대로 AZ 장애 복원력이 향상된다`는 문장은 다음 두 장점을 한꺼번에 표현한 것입니다.

> 서로 다른 AZ에 대기 인스턴스가 2대 있으므로 장애 대응력이 높아집니다. 또한 이 두 인스턴스는 평상시에 읽기 트래픽도 처리할 수 있습니다.

읽을 수 있기 때문에 복원력이 높아지는 것은 아닙니다. 대체 가능한 인스턴스가 두 AZ에 각각 존재하기 때문에 복원력이 높아지는 것입니다.

## 복제 지연

반동기식 복제라고 해서 Reader가 항상 최신 데이터를 보여주는 것은 아닙니다.

예를 들어 현재 상태가 다음과 같을 수 있습니다.

```text
Writer   : 트랜잭션 100까지 적용
Reader 1 : 트랜잭션 100까지 적용
Reader 2 : 트랜잭션 97까지 적용
```

Reader 1은 최신 상태지만 Reader 2는 세 개의 트랜잭션만큼 뒤처져 있습니다.

Reader가 트랜잭션 로그를 받았다는 것과 해당 로그를 실제 조회 데이터에 모두 적용했다는 것은 서로 다릅니다. 로그를 받은 뒤 데이터에 반영하는 데 시간이 필요할 수 있습니다.

Reader endpoint는 연결을 Reader 1 또는 Reader 2로 분산하므로 어느 Reader에 연결됐는지에 따라 조회 결과가 달라질 수 있습니다.

따라서 다음 기준으로 엔드포인트를 선택해야 합니다.

- 방금 저장한 데이터가 반드시 보여야 한다면 Writer endpoint를 사용합니다.
- 약간 오래된 데이터가 반환돼도 괜찮다면 Reader endpoint를 사용합니다.

## 현재 예상 부하

| 구분 | 전체 DB QPS | Reader로 분리 가능한 QPS | Writer에 남는 QPS |
| --- | --- | --- | --- |
| 3년 차 운영 | 약 200 | 약 120 | 약 81 |
| 2배 부하 검증 | 약 400 | 약 239 | 약 162 |

Read Replica가 없다면 Writer가 200~400 QPS 전체를 처리합니다. 이 정도는 인덱스가 적절하고 쿼리가 단순하다면 단일 Writer로 우선 검증할 만한 범위입니다

또한, 조회 비중이 높더라도 절대량은 Peak 약 41.5 Read RPS입니다. 그리고 모든 조회를 Reader로 보낼 수도 없습니다.

| Reader로 보낼 수 있는 조회 | Writer를 사용해야 하는 조회 |
| --- | --- |
| 홈 목록 | 결제 직후 결과 |
| 인기 도서 | 주문 상태 |
| 도서 설명 | 재고·가격 |
| 오래된 리뷰 | 쓰기 직후 사용자 정보 |

## Read Replica 도입 시 추가 부담

Read Replica를 추가하면 같은 Class와 스토리지를 사용하는 DB가 한 대 더 생깁니다. `Writer + Standby`에서 `Writer + Standby + Reader`가 되므로 DB 기본 비용이 대략 50% 증가합니다.

운영 측면에서도 다음 작업이 추가됩니다.

- Writer·Reader Connection Pool 분리
- 조회별 Routing 규칙
- 쓰기 직후 조회를 Writer로 보내는 처리
- Replica Lag 모니터링
- Reader 장애 시 조회 제한 또는 Writer 우회
- Writer로 부하가 한꺼번에 몰리는 상황 방지
- Reader 스키마와 버전 관리

# 최종 선택 및 근거

v2 데이터베이스는 **Amazon RDS for MySQL의 Multi-AZ DB Instance 방식**으로 구성합니다. 서로 다른 두 가용 영역에 Primary와 Standby를 배치하고, 동기식 복제를 통해 데이터를 유지하는 구조입니다.

현재 예상 부하는 약 200 QPS이며 부하 테스트 기준은 약 400 QPS입니다. 적절한 인덱스와 쿼리 최적화를 전제로 하면 단일 Writer로 처리 가능한 범위이므로, 읽기 확장을 위한 Multi-AZ DB Cluster나 Read Replica를 초기부터 도입할 필요는 없다고 판단했습니다.

이번 선택에서 가장 중요한 기준은 처리 성능이 아니라 **장애 복구와 운영 부담**입니다.

EC2 기반 Primary–Standby 구성도 데이터 복제는 가능하지만, 안전한 자동 장애 조치를 구현하려면 Fencing, Witness, 오케스트레이터, 분산 잠금, DNS 또는 Proxy 전환과 같은 추가 구성이 필요합니다. 이러한 장치가 충분하지 않으면 네트워크 단절 시 두 서버가 동시에 Primary로 동작하는 Split-brain이 발생할 수 있습니다. 수동으로 장애 조치를 수행할 경우에도 담당자의 대응 시간과 판단에 따라 복구 시간이 달라지며, 잘못된 승격이나 기존 Primary 차단 누락과 같은 휴먼에러가 발생할 수 있습니다.

RDS Multi-AZ는 Primary 장애 감지, 기존 Primary 격리, Standby 자동 승격, DB Endpoint 전환, 장애 인스턴스 교체와 Standby 재구축을 AWS가 관리합니다. 따라서 인스턴스, 스토리지, 네트워크 또는 가용 영역 장애가 발생했을 때 보다 안전하고 일관된 복구가 가능하며, 목표 복구 시간인 RTO 5분을 달성할 가능성도 높일 수 있습니다.

이에 따라 현재 요구사항에서는 비용과 구조가 더 복잡한 Multi-AZ DB Cluster 대신, **고가용성과 자동 장애 조치에 집중한 Multi-AZ Primary–Standby 구성이 가장 적절합니다.**

다만 장애 조치 과정에서 기존 DB 연결과 실행 중인 쿼리가 종료될 수 있으므로, 애플리케이션에는 연결 재시도와 주문·결제 요청의 멱등성 처리가 필요합니다.
