## 2. 기존 인프라 구조의 한계와 개선

### 2.1. 단일 App 서버

### 2.1.1. 문제 정의

V1은 하나의 `t3.small` App EC2에서 Nginx, Backend와 MySQL을 함께 실행합니다.

```
App EC2
├─ Nginx
├─ Backend
└─ MySQL
```

V2에서는 Peak Traffic이 0.18 RPS에서 50 RPS로 증가합니다. 현재 구조에는 다음과 같은 한계가 있습니다.

- EC2 장애 시 Backend와 MySQL이 함께 중단됩니다.
- Recreate 배포 중에는 요청을 처리할 Backend가 없습니다.
- 트래픽이 증가해도 요청을 나눠 처리할 App 서버가 없습니다.
- Backend와 MySQL이 자원을 공유해 각각 확장하기 어렵습니다.
- 서버 수가 고정되어 있어 트래픽 변화에 대응하기 어렵습니다.

정적 화면은 CloudFront와 S3에서 계속 제공할 수 있지만, App EC2가 중단되면 로그인·검색·리뷰·장바구니·주문·결제 등의 API는 사용할 수 없습니다.

현재 App EC2는 전체 API의 단일 장애 지점(SPOF)이며, Backend와 MySQL이 결합되어 있어 확장에도 한계가 있습니다.

### 2.1.2. Scale-Up과 Scale-Out 비교

| 구분 | Scale-Up | Scale-Out |
|---|---|---|
| 확장 방법 | EC2 사양을 높임 | App EC2 수를 늘림 |
| 가용성 | 단일 장애 지점이 남음 | 다른 서버가 요청 처리 가능 |
| 트래픽 대응 | 변경한 사양을 계속 유지 | 서버 수를 늘리거나 줄일 수 있음 |
| 비용 | 유휴 자원이 발생할 수 있음 | 서버와 로드밸런서 비용이 발생함 |
| 운영 | 비교적 단순함 | 요청 분산과 서버 관리가 필요함 |

#### 1. Scale-Up만으로 부족한 이유

Scale-Up은 기존 EC2의 CPU와 메모리를 늘리는 가장 단순한 확장 방법입니다. 현재 서버의 자원만 부족하다면 구조를 크게 바꾸지 않고 처리량을 높일 수 있습니다.

하지만 App 서버가 한 대인 상태에서는 다음 문제가 남습니다.

- EC2 장애 시 전체 Backend가 중단됩니다.
- 배포 중 요청을 처리할 대체 서버가 없습니다.
- 확장 범위가 단일 인스턴스의 최대 사양에 제한됩니다.
- Peak Traffic에 맞춘 사양을 트래픽이 적은 시간에도 유지해야 합니다.

북적북적은 로그인과 검색뿐 아니라 장바구니·주문·결제를 제공합니다. 

App 서버가 중단되면 주문을 진행하거나 결제 결과를 확인할 수 없습니다. 서비스 규모가 커질수록 같은 시간의 중단도 더 많은 주문 실패와 매출 손실로 이어질 수 있습니다.

따라서 V2에서는 비용 효율성보다 가용성·복구성을 우선합니다. 서버 한 대의 처리량만 높이고 단일 장애 지점을 남기는 Scale-Up만으로는 이 요구사항을 충족하기 어렵다고 판단했습니다.

EC2 장애가 발생할 확률이 높다고 단정할 수는 없습니다. 하지만 현재 구조에서는 한 번의 장애만으로 로그인·검색·주문·결제 API가 모두 중단됩니다. 장애 가능성이 낮더라도 발생했을 때의 영향이 크므로, 성장한 커머스 서비스가 감수하기 어려운 위험입니다.

따라서 장애 발생 확률보다 장애가 서비스 전체로 확산되는 구조를 먼저 개선합니다. [AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_fault_isolation_multiaz_region_system.html)에서도 단일 장애 지점을 줄이기 위해 워크로드를 여러 실행 단위와 가용 영역에 분산하도록 권장합니다.

#### 2. Scale-Out이 필요한 이유

Scale-Out은 같은 역할의 App 서버를 여러 대 실행하고 요청을 나눠 처리하는 방식입니다.

앞서 확인한 단일 장애 지점을 줄이고 주문·결제 요청을 계속 처리하려면 장애가 발생한 서버를 대신할 다른 App 서버가 필요합니다.

북적북적은 사용자가 도서를 검색하고 리뷰를 비교한 뒤 장바구니와 결제로 이동하는 흐름을 가집니다. 이 과정에서 서버가 중단되면 탐색이 끊기고 구매 포기로 이어질 수 있으므로, 일부 App 서버에 문제가 생겨도 사용자 흐름이 이어져야 합니다.

- 한 App 서버가 중단돼도 다른 서버가 요청을 처리할 수 있습니다.
- 일부 서버를 유지한 상태에서 나머지 서버를 순차적으로 배포할 수 있습니다.
- 트래픽이 증가하면 서버를 추가해 전체 처리량을 높일 수 있습니다.
- 트래픽이 감소하면 불필요한 서버를 줄일 수 있습니다.
- 한 서버의 최대 사양에 의존하지 않고 서비스 성장에 맞춰 확장할 수 있습니다.

다만 서버 수만 늘린다고 가용성이 확보되는 것은 아닙니다. 

요청을 정상 서버로 분산하고, 비정상 서버를 요청 대상에서 제외하며, 여러 서버가 동일한 데이터와 사용자 상태를 사용해야 합니다.

따라서 V2에서는 여러 App 서버가 요청을 나눠 처리하고, 한 서버의 장애를 다른 서버가 대신할 수 있는 구조를 검토합니다.

#### 3. Single-AZ와 Multi-AZ 비교

Scale-Out을 적용하더라도 모든 App 서버를 같은 가용 영역에 배치하면 해당 영역의 전원이나 네트워크 장애에 함께 영향을 받을 수 있습니다.

[AWS의 리전 및 가용 영역 설명](https://docs.aws.amazon.com/global-infrastructure/latest/regions/aws-regions-availability-zones.html)에 따르면 AZ 장애의 구체적인 확률은 공개되지 않았지만, 같은 위치의 리소스 가용성에 영향을 주는 장애가 드물게 발생할 수 있습니다.

모든 EC2가 하나의 AZ에 있으면 해당 AZ 장애 시 App 서버 전체를 사용할 수 없습니다.

| 기준 | Single-AZ | Multi-AZ |
| --- | --- | --- |
| 서버 배치 | 하나의 AZ에 배치 | 둘 이상의 AZ에 분산 |
| EC2 장애 | 다른 EC2에서 처리 가능 | 다른 EC2에서 처리 가능 |
| AZ 장애 | 모든 App 서버가 중단될 수 있음 | 정상 AZ에서 요청 처리 가능 |
| 비용·운영 | 비교적 단순함 | 네트워크 구성과 비용 증가 가능 |

Single-AZ에 App 서버를 여러 대 두면 개별 EC2 장애에는 대응할 수 있습니다. 하지만 같은 AZ의 기반 시설에 문제가 생기면 여러 App 서버가 동시에 중단될 수 있습니다. 서버 수를 늘렸더라도 하나의 장애 범위에 모여 있다는 한계가 남습니다.

북적북적은 도서 탐색부터 주문·결제까지 이어지는 서비스이므로 AZ 장애가 전체 API 중단으로 확대되지 않아야 합니다. 

이를 위해 App 서버를 둘 이상의 AZ에 분산하는 Multi-AZ 구성을 검토합니다. 한 AZ에 문제가 생기면 정상 AZ의 App 서버가 요청을 이어서 처리할 수 있습니다.

Multi-AZ 구성에는 AZ별 네트워크 구성이 필요하고, 통신 경로에 따라 데이터 전송 비용도 발생할 수 있습니다. 하지만 V2는 비용 효율성보다 가용성·복구성을 우선하므로 모든 App 서버를 하나의 AZ에 두는 위험을 줄이는 것이 더 중요합니다.

#### 4. Multi-AZ에서 App을 고정 운영하는 경우

가용성을 확보하는 가장 단순한 방법은 두 AZ에 App EC2를 한 대씩 두는 것입니다. 한 EC2나 AZ에 문제가 생기면 다른 AZ의 서버가 요청을 처리할 수 있습니다.

하지만 두 대를 고정하는 것만으로 트래픽 변화까지 대응할 수 있는 것은 아닙니다.

- 한 서버가 중단되면 남은 서버 한 대가 전체 요청을 처리해야 합니다.
- 서버 장애와 Peak Traffic이 겹치면 처리 용량이 부족할 수 있습니다.
- 두 서버의 처리량을 넘는 요청이 들어오면 직접 서버를 추가해야 합니다.
- 장애 서버를 대신할 EC2도 직접 생성하고 설정해야 합니다.

장애 상황에도 Peak Traffic을 처리하도록 Scale-Up으로 보완하려면 두 EC2 모두 전체 Peak를 감당할 수 있는 사양으로 높여야 합니다.

그러나 북적북적은 점심 `12:00~13:00`과 저녁 `18:00~23:00`에 트래픽이 집중될 것으로 예상하므로, 큰 EC2를 계속 실행하면 나머지 시간에는 사용하지 않는 자원이 남습니다.

EC2는 CPU 사용률이 아니라 실행 시간과 인스턴스 사양을 기준으로 과금됩니다. [Amazon EC2 On-Demand 요금](https://aws.amazon.com/ec2/pricing/on-demand/)

반대로 작은 EC2 두 대만 유지하면 집중 시간이나 장애 상황에서 처리 용량이 부족할 수 있습니다. 따라서 평상시에는 가용성에 필요한 최소 서버를 유지하고, 트래픽이 증가하거나 서버가 중단되면 필요한 만큼 서버를 추가할 방법이 필요합니다.

이를 위해 부하에 따라 App 실행 수를 자동으로 늘리거나 줄이는 Auto Scaling을 고려합니다.

#### 2.1.3. App 실행 및 확장 방식 비교

Auto Scaling을 구성하는 방법은 무엇을 늘릴 것인지에 따라 나뉩니다. 비교할 방식은 `ASG + EC2`, `ECS on EC2`, `ECS Fargate`입니다.

| 방식 | 늘리는 단위 | 서버 관리 | 특징 |
| --- | --- | --- | --- |
| ASG + EC2 | EC2 | 팀이 관리 | 서버와 Backend 실행 수가 함께 증가 |
| ECS on EC2 | 컨테이너와 EC2 | 팀이 관리 | ECS가 컨테이너를 관리하고 ASG가 EC2를 관리 |
| ECS Fargate | 컨테이너 | AWS가 관리 | EC2를 직접 운영하지 않고 컨테이너만 관리 |

`ASG + EC2`는 Backend가 실행된 서버를 한 대씩 추가하는 방식입니다. `ECS on EC2`는 Backend 컨테이너와 이를 실행할 EC2 용량을 각각 관리합니다. `ECS Fargate`는 Backend 컨테이너만 관리하고 기반 서버 운영은 AWS에 맡깁니다.

이후에는 가용성·운영 복잡도·비용을 기준으로 세 방식을 자세히 비교합니다.

세 방식 모두 요청을 처리하는 서버가 바뀔 수 있으므로 Backend는 특정 서버에 상태를 저장하지 않아야 합니다. 인증은 JWT로 검증하고, 업로드 파일은 S3에 저장하며, 여러 Backend가 공유할 데이터는 DB나 공용 저장소에서 관리합니다.

#### 1. ASG + EC2

`ASG + EC2`는 Backend 컨테이너가 실행된 EC2를 확장 단위로 사용하는 방식입니다. 현재처럼 EC2마다 Backend 컨테이너 하나를 실행한다면 EC2 한 대가 추가될 때 Backend 실행 단위도 하나씩 늘어납니다.

V1에서는 서버가 부족하거나 중단되면 운영자가 EC2를 생성하고 Backend를 다시 실행해야 합니다. ASG를 사용하면 정해진 범위 안에서 EC2 수를 조절하고, 비정상 EC2를 같은 설정의 새 EC2로 교체할 수 있습니다. 따라서 두 AZ에 필요한 서버 수를 유지하면서 트래픽 증가와 서버 장애에 자동으로 대응할 수 있습니다. [EC2 Auto Scaling의 이점](https://docs.aws.amazon.com/autoscaling/ec2/userguide/auto-scaling-benefits.html)

현재 계획에서는 EC2 수와 Backend 컨테이너 수가 함께 변하므로 두 수량을 별도로 관리할 필요가 없습니다. 기존의 EC2·Docker 운영 방식을 유지하면서 서버 확장과 장애 교체를 자동화할 수 있다는 점이 장점입니다.

반면 ASG가 직접 관리하는 대상은 EC2입니다. Backend 컨테이너의 실행과 재시작, 로그 수집, 상태 확인과 배포 절차는 팀이 구성해야 합니다. 운영체제와 Docker의 보안 패치도 직접 관리해야 하므로 서버 운영 부담은 남습니다.

새 EC2가 요청을 처리하려면 인스턴스 생성, OS 부팅, Backend 실행과 상태 확인을 거쳐야 하므로 확장에 시간이 걸립니다. 새 서버가 준비될 때까지는 기존 서버가 요청을 처리해야 하며, 가용성을 위해 유지하는 최소 EC2 비용도 계속 발생합니다.

#### 2. ECS on EC2

ECS on EC2는 EC2 위에서 컨테이너를 실행하되, 컨테이너의 배치와 상태를 ECS가 관리하는 방식입니다. ECS에서 컨테이너 실행 단위를 `Task`라고 하며, ECS Service는 필요한 Task 수를 유지하고 비정상 Task를 새 Task로 교체합니다.

Capacity Provider는 ECS의 Task 수요와 ASG의 EC2 용량을 연결합니다. 관리형 확장을 사용하면 새 Task를 배치할 공간이 부족할 때 ASG에 EC2 확장을 요청합니다.

```
Backend 컨테이너 수 증가
→ ECS가 실행 공간 확인
→ 공간이 부족하면 ASG가 EC2 추가
→ 새 EC2에 Backend 컨테이너 배치
```

ECS on EC2를 사용하면 종료된 Backend Task를 자동으로 교체하고, 같은 설정으로 여러 EC2에 배치할 수 있습니다. 새 버전도 Task 단위로 순차 배포할 수 있어 컨테이너의 배포와 상태 관리를 자동화하기 좋습니다.

반면 ECS는 Task 수를, ASG는 EC2 수를 관리하므로 두 계층의 용량과 확장 상태를 함께 확인해야 합니다. ECS Cluster, Service와 Capacity Provider 설정이 추가되지만 EC2와 운영체제 관리도 그대로 남습니다. [AWS ECS Capacity Provider](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/asg-capacity-providers.html)

북적북적은 현재 App EC2마다 Backend 컨테이너 하나를 실행할 계획입니다. 이 배치 방식을 유지하면 Backend Task가 하나 증가할 때 EC2도 한 대 추가되어야 합니다. 따라서 여러 Task를 EC2의 남은 자원에 배치하여 서버를 효율적으로 사용하는 이점은 현재 구조에서 제한적입니다. 다만 Task 자동 교체와 순차 배포 같은 컨테이너 관리 기능은 그대로 활용할 수 있습니다.

또한 실행 가능한 EC2 용량이 부족하면 새 EC2가 준비될 때까지 Task가 대기하므로 EC2 기동 지연은 남습니다.

한 EC2에 여러 컨테이너를 배치하거나 여러 애플리케이션을 컨테이너 단위로 운영한다면 ECS가 제공하는 배치와 상태 관리의 이점이 더 커집니다.

#### 3. ECS Fargate

Fargate는 EC2를 직접 운영하지 않고 Backend 컨테이너를 Task 단위로 실행하는 방식입니다. 팀은 컨테이너 이미지와 CPU·메모리, 실행 수를 정하고 기반 서버와 OS는 AWS가 관리합니다.

ECS on EC2처럼 Task를 실행할 EC2 용량을 따로 관리하지 않아도 되므로 구조와 운영이 단순합니다. 인프라 담당자가 개발을 병행하는 북적북적에는 분명한 장점입니다.

대신 정해진 CPU·메모리 조합에서 사양을 선택해야 하고 기반 서버를 직접 제어할 수 없습니다. 새 Task도 이미지 다운로드와 상태 확인을 거쳐야 하므로 바로 요청을 처리할 수 있는 것은 아닙니다. 또한 Backend를 계속 실행하면 트래픽이 적어도 지정한 자원에 대한 비용이 발생합니다.

#### 4. 비용 비교

- 서울 리전의 On-Demand 요금
- 한 달 30일, 하루 24시간 실행: `720시간`
- Multi-AZ 구성을 위해 실행 단위 2개 유지

| 방식 | 실행 단위 | 1개당 월 비용 | 2개 월 비용 |
| --- | --- | --- | --- |
| ASG + EC2 | `t3.small` + gp3 30GB | 약 $21.46 | 약 $42.91 |
| ECS on EC2 | `t3.small` + gp3 30GB | 약 $21.46 | 약 $42.91 |
| ECS Fargate | 1 vCPU + 2GB | 약 $40.88 | 약 $81.76 |

ECS on EC2는 ECS 자체에 별도 요금이 없으므로 동일한 EC2 사양과 수량을 사용하면 ASG + EC2와 기본 실행 비용이 비슷합니다. [Amazon ECS 요금](https://aws.amazon.com/ecs/pricing/)

Fargate는 EC2 관리가 필요 없는 대신 실행 단위 두 개를 한 달 동안 유지하면 EC2 기반 방식보다 약 $38.85 더 듭니다. [AWS Fargate 요금](https://aws.amazon.com/fargate/pricing/)

#### 5. App 실행 방식 선택

세 방식 모두 Multi-AZ와 자동 확장을 구성할 수 있습니다. 

북적북적은 필요한 가용성과 확장성을 충족하면서 운영 복잡도와 비용의 균형이 맞는 `ASG + EC2`를 선택합니다.

- EC2마다 Backend 컨테이너 하나를 실행하므로 EC2 수와 Backend 실행 수를 따로 관리할 필요가 없습니다.
- Multi-AZ 배치, 서버 확장과 비정상 EC2 교체는 ASG로 구성할 수 있습니다.
- ECS on EC2를 사용해도 EC2와 운영체제 관리가 남으며, 현재 구조에서는 컨테이너 배치로 얻는 이점이 제한적입니다.
- Fargate는 운영 부담이 가장 작지만 현재 계획 사양에서는 EC2 기반 방식보다 비용이 높습니다.
- 기존 EC2·Docker 운영 경험을 유지할 수 있습니다.

대신 컨테이너 실행과 배포, 로그 수집, OS 패치는 직접 관리해야 하며 EC2 기동 지연도 남습니다. 이후에는 이러한 한계를 어떻게 보완할지 검토합니다.
